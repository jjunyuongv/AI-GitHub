### 전제 셋이 다 뒤집혔다

**① "답변이 파일명 자리에 클래스명을 적었다"가 아니다.** `looks_like_path()` 는
`"/" 포함` 또는 `.확장자 끝` 만 봤으므로 **맨 클래스명은 애초에 후보가 아니다.**
171건 전체에서 맨 이름이 `current_file` 이 된 사례는 0건이다.

데모 답변의 실제 경위:

| 줄 | 백틱 | `current_file` |
|---|---|---|
| L3 | `src/main/java/.../websocket/` | **디렉터리**가 파일명이 됐다 |
| L5 | `ChatSocketConfig` | 안 바뀜 → L3 의 디렉터리가 붙는다 |
| L7 | …`/myChatServer`… | **엔드포인트**가 덮었다 |
| L9·L13·L15 | 맨 클래스명뿐 | 안 바뀜 → L7 이 계속 붙는다 |

클래스명은 **파일명 자리에 적힌 것이 아니라 그 자리를 비운 것**이고, "직전에 언급된
것을 쓴다"는 폴백이 빈 자리를 엉뚱한 것으로 채웠다. **한 줄의 오탐이 다음 줄들까지
오염시킨다** — 이것이 171건을 크게 만든 증폭기다.

**② "실제 파일인데 접미사 매칭이 실패했다"는 0건이다.** 171건을 문자열 유형으로 갈랐다:

### 클래스명 → 파일 매핑(D)은 안 한다 — 틀린 링크를 만든다

언어 관례는 확실하다: Java 는 첫 타입명 == 파일명이 **72/72(100%)** 이고 stem 충돌 0.
Python 3/86 · JS 0/21 · JSX 2/20 이고 marryday 는 충돌 stem 이 33종
(`admin` → `.py`/`.css`/`.js`/`.html`). **언어별 분기는 필요 없다** — 기존 "둘 이상
맞으면 버린다"가 그대로 막고, 실제로 D 39건 중 38건이 Java 다.

**그런데도 안 한다. 데모 답변에서 틀린 링크가 실증됐다:**

```
L7  …`ChatHandler`를 `/myChatServer` 경로에 등록하며, `setAllowedOrigins("*")`…(24-25행)

   심볼 매핑이 고르는 것 : ChatHandler.java       24-25행 = CLIENTS.put(session.getId(), session);
   정답                : ChatSocketConfig.java   24-25행 = .setAllowedOrigins("*") / .withSockJS();
```

같은 줄에 유일하게 매핑되는 심볼이 **그 줄이 말하는 파일이 아니다.** 옳은 신호는 같은
줄이 아니라 위쪽 소제목이었다. `resolve_path` 가 경계한 그것 — "아무거나 고르면 화면이
엉뚱한 파일을 열어 준다" — 이 그대로 적용되고, **내용이 그럴듯해서 더 알아채기 어렵다.**

### 조여도 링크가 줄지 않는 근거

보관되는 파일은 `language_for()` 가 아는 확장자뿐이고(`fetch_source_files`), 경로 해석은

어떤 보관 경로와도 맞을 수 없다.** 거르는 것은 링크가 될 수 없었던 것뿐이다 —
실측으로도 링크가 준 건은 0건이다.

### 기여도가 크게 갈렸다 — 2번은 +1건이다

| | 인용 | 유실 | 귀속 정확 |
|---|---|---|---|
| 전 | 535 | 358 | 163/176 = 92.6% |
| 1번만 (조이기) | **671** | 222 | 201/220 = 91.4% |
| 1+2 (풀리는 것 우선) | 672 | 221 | 201/220 = 91.4% |
| 1+2+3 (평문) | **807** | **86** | 229/254 = 90.2% |

**2번은 +1건이다.** 조이고 나면 라우트가 애초에 후보에서 빠지므로 "풀리는 것 우선"이
할 일이 거의 없다 — 조사 때 센 B 33건은 **옛 느슨한 판정 기준의 수**였다.
규칙은 남긴다(안 풀리는 파일명이 풀리는 것을 덮는 일은 실재한다) 다만 **대역을 따로
둔다** — 셋을 한 대역에 뭉치면 +1 짜리 규칙을 통째로 지우는 변이가 조용히 통과한다.

**평문(3번)이 더 위험하지 않았다.** 조이기는 +136건에 오귀속 +6, 평문은 +135건에
오귀속 +6 — **비율이 4.4% 로 같다.**

### 검증 — 관문 둘 다 통과

옛 파서를 `git show HEAD:` 로 떠서 **같은 답변에 둘 다 돌려 건별로 대조**했다.

| 확인 | 결과 |
|---|---|
| 인용 | 535 → **807** |
| 유실 | 358 → **86** (파일명 없음 78 · 접미사 중복 7 · 범위 너무 넓음 1) |
| **경로 해석 실패** | 171 → **0** |
| **관문 1** — 가짜 파일명이 실제 경로에 맞은 건 | **0건** |
| **관문 2** — 전에 `correct` 였는데 후에 `wrong` 이 된 건 | **0건** |
| 행 번호 정확도 | 72.4%(118/163) → **70.7%(162/229)** |
| 귀속 정확률 | 92.6% → 90.2% |

**정확도가 1.7%p 내렸는데 이것은 나빠진 것이 아니다.** 모수가 163 → 229 로 40% 늘었고
정확이 118 → 162(+44), 틀림이 45 → 67(+22)다. **전에 맞던 것이 틀리게 된 건은 0이다** —
늘어난 22건은 **원래 아예 안 뽑히던** 인용이다. 새로 채점된 66건의 정확도가 66.7% 로
기존 72.4% 보다 낮아서 평균이 내려갔을 뿐이다.

**감추지 않는 것이 이 기능의 목적이다**(STATUS §2.4). 링크를 272건 늘리면서 그중 일부가
틀린 행을 가리키는 것은, 그 272건을 아예 안 보여 주는 것보다 낫다는 판단이다.

`_verdict` 의 `wrong` 은 **조각이 지목한 파일 안에 있되 범위 밖**일 때만 나온다.
그러므로 늘어난 67건의 `wrong` 은 전부 **파일은 맞고 행이 틀린** 것이다 — 오귀속은
`unknown` 칸에 숨는데 그쪽은 102 → 107(+5)에 그쳤다.
