## 0단계: 답변 품질 판정 기준 고정 - 2026-08-21

tool use 를 붙이기 전에 **자를 먼저 만든다.** tool use 는 검색을 반복하는 경로를 만드는데,
그 경로의 고유한 실패는 *없는 것을 계속 뒤지다 지어내는 것*이다.

**지금 있는 자는 그걸 못 잡는다.** `test_citation_quality.py` 의 인용 정확도는 "답변이
정답 파일을 짚었는가"를 세는데, 정답이 애초에 없는 질의에서는 짚을 파일이 없다 —
날조와 침묵이 똑같이 0점으로 보인다. 그래서 **거절 축**을 따로 만든다.

이 단계에서 tool use 는 붙이지 않는다. 브랜치 `eval/answer-quality`.

### 정한 것과 그 이유

**팔을 저장소 이름으로 가르지 않는다.** `measure_bundle()` 로 잰 번들 토큰이 임계값
이하일 때만 `full` 팔을 붙인다 — 프로덕션이 우회를 판정할 때 쓰는 바로 그 함수라
하네스와 서비스의 기준이 갈리지 않는다. 임계값을 바꾸면 팔도 자동으로 따라간다.
실측: apns4j 34,467 · air 62,380 · marryday 1,057,764 (임계값 57,000).

**거절 문구를 프롬프트에 f-string 으로 끼워 넣지 않았다.** 끼워 넣으면 정합성이
자동으로 맞아 보이지만 그 순간 검사가 동어반복이 되어, 문구가 갈라져 하네스가 조용히
0점을 매기는 상황을 못 잡는다. 리터럴로 두고 포함 여부를 검사하는 쪽이 **실제로 깨진다**
(아래 변이에서 확인).

**거절 질의를 기존 목록에 섞지 않은 진짜 이유는 두 개다.** 하나는 Recall@8 분모가
바뀌는 것이고, 다른 하나는 `_cited()` 가 `answers` 없는 질의에서 **언제나 False** 라는
것이다. 섞으면 그 False 들이 분자에서 빠진 채 분모만 늘려 인용 정확도가 조용히
희석되고, 그 하락이 개선 실패로 오독된다. 이걸 테스트로 못 박았다.

## 0단계 기준선 측정 — 자가 새는 것을 확인했다 - 2026-08-21

**이 측정은 1단계 tool use 의 비교 기준선이다.** 이 숫자가 없으면 tool use 를 붙여도
좋아졌는지 나빠졌는지 말할 수 없다. 이번 실행에서 무언가를 채택하거나 기각하지 않는다.

### 판정 규칙 — 측정 **전에** 고정했다

`tests/test_citation_quality.py` docstring 에 박아 두고 측정을 돌렸다. 결과를 보고
정하면 측정이 아니라 사후 합리화가 된다.

    A. 인용 정확도가 기준선보다 떨어지면 기각
    B. A 가 동률이면 거절 정확도를 본다. 떨어지면 기각
    C. A·거절이 올라도 질문당 비용이 COST_RATIO_LIMIT(3.0)배를 넘으면
       전면 도입하지 않고 "큰 저장소 전용"으로만 켠다

### 사전 준비

색인 생성과 과금 측정을 한 실행에 섞지 않았다 — marryday 는 4,365청크라 오래 걸리고,
그 도중에 죽으면 이미 쓴 API 비용이 날아간다. 세 세트 다 **현행 규칙(822bb217)의
활성 빌드가 이미 있어** 재색인은 필요 없었다 (air 236 · marryday 4,365 · apns4j 168청크).
`active_build_id()` 는 규칙 버전을 보지 않으므로 낡은 색인도 '활성'이다 — 그래서
빌드의 `chunk_rule` 을 따로 대조했다.

### 거절 실패 15건을 전부 읽었다 — **날조 0건, 전부 자의 문제다**

이것을 가르지 않으면 기준선을 잘못 읽는다. 실패한 15건 모두 모델이 "없다"고 정확히
답했고, **규정 문구를 글자 그대로 쓰지 않았을 뿐이다.** 짧게 답하려다 생략한 것도
아니다 — 오히려 근거를 더 길게 댔다.

    [ap_ab_05] 검색된 코드 범위에는 프록시 서버 설정 관련 내용이 없습니다.
               SecuritySocketFactory 는 ... sslSocketFactory.createSocket(host, port)
               로 직접 대상 호스트에 연결하는 방식입니다(119-123행).

패턴이 하나다. 규정 문구는 `검색된 범위에는 없습니다` 인데 모델은 거의 항상
**"검색된 `코드` 범위에는 … 없습니다"** 로 쓴다 — 한 단어가 끼어들어 연속 문자열
매칭이 깨진다. apns4j RAG 가 0.0 인 것은 6건 전부 이 변형이었기 때문이다.

**`full` 팔은 구조적으로 더 심하다.** 전체 소스가 왔을 때 "검색된 범위" 표현을 쓰지
말라고 프롬프트가 막고 있어서, 모델은 "저장소 전체 소스를 확인한 결과 … 존재하지
않습니다"로 답한다. 이건 규정된 두 문구 어디에도 안 걸린다 —
**프롬프트가 요구하는 대로 답할수록 자가 0점을 주는 구조다.**

### 자의 한계 — 절대값으로 읽지 말 것

문구 매칭은 "지어내지 않았는가"의 **대리 지표**다. 이번 측정이 그 한계를 실측으로
보여줬다: 거절 정확도 0.0 은 "6건 다 지어냈다"가 아니라 "6건 다 규정 표현을 안 썼다"였다.
두 팔에 같은 자를 대므로 **비교**에는 쓸 수 있지만, 절대값을 품질로 읽으면 정반대로
틀린다. 특히 apns4j RAG 의 0.0 은 바닥 효과라 1단계에서 올라갈 수밖에 없다 —
그 상승을 tool use 의 성과로 읽으면 안 된다.

**자를 고치는 것은 다음 과제로 남긴다.** 지금 고치면 기준선과 1단계가 다른 자로
재게 된다. 고친다면 (a) 프롬프트 문구를 모델이 실제로 쓰는 표현에 맞추거나,
(b) 매칭을 정규식으로 느슨하게 하거나, (c) 전체 주입용 거절 문구를 따로 규정하는
세 갈래다. 어느 쪽이든 **자를 바꾼 뒤에는 기준선을 다시 재야 한다.**

### 부재 근거 하나가 불완전했다 — `ap_ab_02`

`http2`·`HTTP/2` 0회만 확인했는데, 프로토콜 이름이 아니라 **엔드포인트 주소**로 있었다:

    RESTFUL_PRODUCTION("api.push.apple.com", 443),   // HTTP/2 게이트웨이

전송 구현은 여전히 레거시 바이너리뿐이라 "없는 것"이라는 판정 자체는 맞지만
`why_absent` 는 틀렸다. **모델이 나보다 정확했다** — 게이트웨이 상수는 있으나 실제
요청을 만드는 로직은 없다고 갈라 답했다. 부재를 확인할 때 기능 이름만 찾으면
이렇게 샌다. 도메인 식별자(호스트·포트·상수명)도 함께 봐야 한다.

### 함정: `-m billed` 만 쓰면 조용히 아무것도 안 돈다

docstring 이 적어 둔 명령이 그랬다(0단계 이전부터). `conftest` 의 opt-in 게이트는
마커마다 **따로** 물어서, 이 모듈에 걸린 `evaluation` 마커가 `-m` 에 없으면 그것만으로
건너뛴다. 0.9초에 `sss` 로 끝나고 로그 파일도 안 생긴다. 과금이 없었던 것은 다행이지만,
"측정을 돌렸다"고 착각하기 딱 좋은 모양이다.
`-m "billed and evaluation"` 으로 고치고 docstring 에 이 사실을 적었다.
