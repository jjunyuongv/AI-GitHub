## 0단계: 답변 품질 판정 기준 고정 - 2026-08-21

tool use 를 붙이기 전에 **자를 먼저 만든다.** tool use 는 검색을 반복하는 경로를 만드는데,
그 경로의 고유한 실패는 *없는 것을 계속 뒤지다 지어내는 것*이다.

**지금 있는 자는 그걸 못 잡는다.** `test_citation_quality.py` 의 인용 정확도는 "답변이
정답 파일을 짚었는가"를 세는데, 정답이 애초에 없는 질의에서는 짚을 파일이 없다 —
날조와 침묵이 똑같이 0점으로 보인다. 그래서 **거절 축**을 따로 만든다.

이 단계에서 tool use 는 붙이지 않는다. 브랜치 `eval/answer-quality`.

### 정한 것과 그 이유

**팔을 저장소 이름으로 가르지 않는다.** `measure_bundle()` 로 잰 번들 토큰이 임계값
이하일 때만 `full` 팔을 붙인다 — 프로덕션이 우회를 판정할 때 쓰는 바로 그 함수라
하네스와 서비스의 기준이 갈리지 않는다. 임계값을 바꾸면 팔도 자동으로 따라간다.
실측: apns4j 34,467 · air 62,380 · marryday 1,057,764 (임계값 57,000).

**거절 문구를 프롬프트에 f-string 으로 끼워 넣지 않았다.** 끼워 넣으면 정합성이
자동으로 맞아 보이지만 그 순간 검사가 동어반복이 되어, 문구가 갈라져 하네스가 조용히
0점을 매기는 상황을 못 잡는다. 리터럴로 두고 포함 여부를 검사하는 쪽이 **실제로 깨진다**
(아래 변이에서 확인).

**거절 질의를 기존 목록에 섞지 않은 진짜 이유는 두 개다.** 하나는 Recall@8 분모가
바뀌는 것이고, 다른 하나는 `_cited()` 가 `answers` 없는 질의에서 **언제나 False** 라는
것이다. 섞으면 그 False 들이 분자에서 빠진 채 분모만 늘려 인용 정확도가 조용히
희석되고, 그 하락이 개선 실패로 오독된다. 이걸 테스트로 못 박았다.

### 거절 실패 15건을 전부 읽었다 — **날조 0건, 전부 자의 문제다**

이것을 가르지 않으면 기준선을 잘못 읽는다. 실패한 15건 모두 모델이 "없다"고 정확히
답했고, **규정 문구를 글자 그대로 쓰지 않았을 뿐이다.** 짧게 답하려다 생략한 것도
아니다 — 오히려 근거를 더 길게 댔다.

    [ap_ab_05] 검색된 코드 범위에는 프록시 서버 설정 관련 내용이 없습니다.
               SecuritySocketFactory 는 ... sslSocketFactory.createSocket(host, port)
               로 직접 대상 호스트에 연결하는 방식입니다(119-123행).

패턴이 하나다. 규정 문구는 `검색된 범위에는 없습니다` 인데 모델은 거의 항상
**"검색된 `코드` 범위에는 … 없습니다"** 로 쓴다 — 한 단어가 끼어들어 연속 문자열
매칭이 깨진다. apns4j RAG 가 0.0 인 것은 6건 전부 이 변형이었기 때문이다.

**`full` 팔은 구조적으로 더 심하다.** 전체 소스가 왔을 때 "검색된 범위" 표현을 쓰지
말라고 프롬프트가 막고 있어서, 모델은 "저장소 전체 소스를 확인한 결과 … 존재하지
않습니다"로 답한다. 이건 규정된 두 문구 어디에도 안 걸린다 —
**프롬프트가 요구하는 대로 답할수록 자가 0점을 주는 구조다.**

### 자의 한계 — 절대값으로 읽지 말 것

문구 매칭은 "지어내지 않았는가"의 **대리 지표**다. 이번 측정이 그 한계를 실측으로
보여줬다: 거절 정확도 0.0 은 "6건 다 지어냈다"가 아니라 "6건 다 규정 표현을 안 썼다"였다.
두 팔에 같은 자를 대므로 **비교**에는 쓸 수 있지만, 절대값을 품질로 읽으면 정반대로
틀린다. 특히 apns4j RAG 의 0.0 은 바닥 효과라 1단계에서 올라갈 수밖에 없다 —
그 상승을 tool use 의 성과로 읽으면 안 된다.

**자를 고치는 것은 다음 과제로 남긴다.** 지금 고치면 기준선과 1단계가 다른 자로
재게 된다. 고친다면 (a) 프롬프트 문구를 모델이 실제로 쓰는 표현에 맞추거나,
(b) 매칭을 정규식으로 느슨하게 하거나, (c) 전체 주입용 거절 문구를 따로 규정하는
세 갈래다. 어느 쪽이든 **자를 바꾼 뒤에는 기준선을 다시 재야 한다.**

### 부재 근거 하나가 불완전했다 — `ap_ab_02`

`http2`·`HTTP/2` 0회만 확인했는데, 프로토콜 이름이 아니라 **엔드포인트 주소**로 있었다:

    RESTFUL_PRODUCTION("api.push.apple.com", 443),   // HTTP/2 게이트웨이

전송 구현은 여전히 레거시 바이너리뿐이라 "없는 것"이라는 판정 자체는 맞지만
`why_absent` 는 틀렸다. **모델이 나보다 정확했다** — 게이트웨이 상수는 있으나 실제
요청을 만드는 로직은 없다고 갈라 답했다. 부재를 확인할 때 기능 이름만 찾으면
이렇게 샌다. 도메인 식별자(호스트·포트·상수명)도 함께 봐야 한다.

### 함정: `-m billed` 만 쓰면 조용히 아무것도 안 돈다

docstring 이 적어 둔 명령이 그랬다(0단계 이전부터). `conftest` 의 opt-in 게이트는
마커마다 **따로** 물어서, 이 모듈에 걸린 `evaluation` 마커가 `-m` 에 없으면 그것만으로
건너뛴다. 0.9초에 `sss` 로 끝나고 로그 파일도 안 생긴다. 과금이 없었던 것은 다행이지만,
"측정을 돌렸다"고 착각하기 딱 좋은 모양이다.
`-m "billed and evaluation"` 으로 고치고 docstring 에 이 사실을 적었다.

**채점기를 고칠 때마다 LLM 을 다시 부를 이유가 없다.**

### 채점기는 문장 구조에서 유도했다 — 정규식을 늘린 것이 아니다

거절 문장은 예외 없이 **"[어디를 봤는가] + [거기에 없다]"** 두 조각이다. 그래서 조각을
따로 정의하고 한 문장 안에서 이 순서로 나타나는지만 본다.

| 조각 | 상수 | 무엇 |
|---|---|---|
| 스코프 | `REFUSAL_SCOPES` (5) | 검색된… · 검색 결과 · 주어진/제공된 정보·코드·소스 · 전체 소스 · 코드 전체 |
| 부정 | `REFUSAL_NEGATIONS` (8) | 없다 · 보이지 않 · 존재하지 않 · 찾을 수 없 · 확인되지 않 · 알 수 없 … |
| 양보 | `REFUSAL_CONCESSIONS` (1) | "…있지만/…보이지만" — **거절이 아니다** |

**첫 문장만 본다. 이것이 가장 중요한 조임쇠다.** 프롬프트가 "근거가 없으면 … 한 문장으로
밝히라"고 요구하므로 진짜 거절은 답변을 열면서 나온다. 실측에서도 거절 질의 24건 전부가
첫 문장에서 거절했다. 본문 어디든 보면 **근거를 대고 나서 덧붙인 단서**까지 거절로 잡힌다.

### 방어선을 세우다가 3번 요구를 하나 바꿨다

원래 요구는 "정답이 있는 행이 **하나라도** 거절로 잡히면 실패"였다. 그대로 두면
**채점기를 틀리게 만들어야** 만족된다 — 검색이 못 찾아 모델이 **실제로 거절한** 답변이
정답 있는 질의에도 있기 때문이다(`ko_04`·`ko_05`·`py_ko_07`·`py_id_05`·`py_id_06`).
그것을 "거절이 아니다"라고 재는 자가 오히려 고장 난 자다.

그래서 방어선을 **"정답 파일을 짚은 답변(`_cited`)이 거절로도 잡히면 실패"** 로 바꿨다.
막으려던 것("지어낸 답 + 면피 한 줄"이 거절로 통과)은 그대로 막으면서, 자를 틀리게
만들지 않는다. 그리고 이 조건은 실제로 **한 건을 잡아냈다**:

    [apns4j/rag] ap_ko_06
    검색된 코드 범위에서는 실패 알림을 캐시하는 부분(`ApnsChannel.java`)은 보이지만,
    재전송을 수행하는 로직 자체는 확인되지 않습니다.

`ApnsChannel.java` 를 정확히 짚으면서 일부만 없다고 한 답변이다. 여기서 양보 규칙이
나왔다 — 데이터에 맞춰 깎은 것이 아니라, **방어선이 구조적 빈틈을 가리켰다.**
모호한 문장은 거절로 세지 않는다. 적게 세는 쪽으로 틀려야 tool use 가 실제보다
정직해 보이지 않는다.

숫자로 정리하면 이번 측정 89건 = 거절 질의 24 + 정답 있는 질의 **65** 다
(과제 문안의 74 는 계산 착오다). 거절 24건 중 옛 자로 통과한 것이 9, 실패가 15였다.

## 1단계 착수 전 조사 — 소스가 없다는 것을 확인했다 - 2026-08-22

고치지 않았다. **조사가 1단계를 세 군데 바꿨다.**

### 결론부터 — 도구가 서빙할 원문이 어디에도 없다

`fetch_source_files()` 로 받은 `{경로: 내용}` 은 메모리에만 산다. 종착지가 셋인데
(정적분석 집계 · 청킹·임베딩 · 전체 주입 번들) **원문이 남는 것은 마지막 하나뿐**이다.

그 하나가 `repo_snapshots.source_bundle` 인데 `FULL_INJECTION_MAX_TOKENS`(57,000)
이하일 때만 채워진다. **소스가 이미 프롬프트에 통째로 들어가 도구가 필요 없는 저장소에만
원문이 있고, 도구가 절실한 큰 저장소에는 없다.** 이 역설이 곧 다음 절 작업의 이유다.

### 청크로는 복원할 수 없다 — 추정이 아니라 실측이다

STATUS.md §4 는 "`_merge_small` 이 떨어진 조각을 이어붙여 줄이 어긋난다"고만 적어
두었다. 실제로 재 보니 **어긋나는 것은 줄 번호가 아니라 내용 자체였다.**
로컬 소스 캐시 3개를 `chunk_file()` 에 그대로 통과시켰다(LLM·GitHub·임베딩 호출 0회):

| 저장소 성격 | 파일 | 청크 | 완전복원 가능 파일 | 사라진 비어있지 않은 줄 | content 줄수 ≠ end−start+1 |
|---|---|---|---|---|---|
| 작은 Java 라이브러리 | 32 | 168 | **0 / 32** | **11.1%** (233/2,096) | **48.8%** |
| 중간 Java 웹앱 | 47 | 236 | 6 / 47 | **12.7%** (407/3,207) | 33.9% |
| 큰 Python/JS | 181 | 4,364 | 59 / 181 | **8.5%** (5,153/60,730) | 13.8% |

**48.8% 가 STATUS.md 의 수치와 정확히 일치했다 — 그 측정이 이 저장소였고, 검산이 된다.**

**이 값들은 하한이다.** 이 실행은 `_split_by_tokens()` 를 태우지 않았다(임베딩 모델
미설치 환경). 프로덕션은 거기서 한 번 더 자르고 40자 미만 부스러기를 또 버린다.

### 줄이 사라지는 코드상 위치 네 곳

- `chunker.chunk_file:264` — `IMPORT_NODES` 최상위 자식을 **통째로 건너뛴다.**
  import 줄은 인덱스에 애초에 존재하지 않는다
- `chunker._node_chunks:194-206` — 컨테이너는 `헤더(start→inner[0].start)` + `inner 정의들`
  만 낸다. **inner 정의 사이의 틈**(필드·주석·빈 줄)과 마지막 정의 뒤 꼬리는 어느 청크에도
  안 들어간다
- `chunker._merge_small:236` — `len(content.strip()) < 40` 인 청크를 **버린다**
- `chunker._merge_small:228` — 떨어진 두 조각을 `"\n"` 으로 붙이고 `end_line` 만 뒤쪽
  것으로 바꾼다. 사이 줄은 없는데 범위는 이어진 것처럼 보인다 — **48.8% 의 정체**

반대로 `_line_chunks` 의 `OVERLAP_LINES = 3` 은 같은 줄을 **중복**시킨다.
청크 집합은 원본의 부분집합도 아니고 상위집합도 아니다. **이어붙이기로 복원이 안 될 뿐
아니라, 복원했다고 착각하면 조용히 틀린다.**

### 캐시 접두사는 도구 호출에 견딘다 — 새는 곳은 꼬리다

`cache_control` 은 정확히 **2개**다(상한 4개 중): `system` 블록과 `messages[0]`
(스냅샷 컨텍스트 + 있으면 번들). 렌더 순서가 `tools` → `system` → `messages` 이므로

- **`tools` 를 추가하는 것**은 위치 0 이라 두 브레이크포인트를 한 번 무효화한다.
  배포 시점 1회이고, 도구 목록이 요청마다 같기만 하면 그 뒤로는 새 접두사로 안정된다.
  → **도구 목록을 저장소마다 다르게 하지 말 것.** 조건부 시스템 섹션과 같은 부류의
  조용한 무효화다
- **라운드트립이 쌓이는 것**은 브레이크포인트 **뒤**에 붙으므로 접두사를 깨지 않는다.
  `messages[0]` 의 브레이크포인트는 자기 앞에 system 밖에 없어 20블록 되돌아보기 창에도
  안 걸린다

**즉 캐시는 견딘다. 새는 곳은 브레이크포인트 뒤의 꼬리다** — 지금 거기에 `history` +
`snippets` + `question` 이 통째로 들어 있고, 라운드트립마다 정가로 다시 청구된다.

### 비용 식과 검산

P = 캐시 접두사, H = 이력, S = 미리 넣은 스니펫, q = 질문, aᵢ·rᵢ = i번째 호출의
출력·tool_result. 호출 N회(도구 N−1회 + 최종 답변 1회):

    입력 청구 = N·(0.1·P + H + S + q) + Σᵢ₌₁^{N−1} (N−i)·(aᵢ + rᵢ)
    출력 청구 = Σ aᵢ

앞항이 N에 선형, 뒷항이 **N에 이차**다. 기준선은 N=1 인 같은 식이다.

**식을 기준선으로 검산했다.** air/rag 기록(P=1,140 · H=0 · S+q≈2,300 · a≈330, 도입가 $2/$10):

    (0.1×1140 + 2300)×$2/1M + 330×$10/1M = $0.008128

기록된 `avg_cost_usd` 는 **$0.008155**. 식이 맞는다.

작은 저장소가 또 빠져 나가 위 역설이 그대로 남는다.**

**상태 열을 두지 않았다.** "보관됐는가"는 `sources.count() > 0` 으로 답하고 "왜 안 됐는가"는

## 1단계: 순수 tool use — 구현과 무과금 검증 (측정 전 정지) - 2026-08-22

브랜치 `feat/tool-use`. **하이브리드가 아니라 순수 tool use 다** — 스니펫 사전 주입을 빼고
`search_code` 를 도구로 내렸다. 근거는 위 조사의 비용표다: 미리 넣은 스니펫은 캐시
브레이크포인트 **뒤**라 라운드트립마다 정가로 되풀이 청구되고, 3회에 3.78배가 되어
판정 기준 C(3배)를 넘는다. 도구만 쓰면 같은 3회가 2.11배다.

### 도구는 셋. 더 만들지 않았다

`Back/app/services/tools.py` 가 스키마와 **스냅샷에 묶인 실행기**를 만든다.
`claude_client` 는 DB·검색을 모른다 — LLM 어댑터로 남겼고, `api/chat.py` 가 둘을 잇는다.

| 도구 | 감싼 것 |
|---|---|
| `search_code(query)` | `indexer.search_code` → `indexer.format_snippets` |
| `read_file(path, start_line, end_line)` | `sources.get_file` → `context_builder.number_lines` |
| `grep(pattern)` | `sources.grep` (신규) |

**`start_line`·`end_line` 을 `required` 에 넣었다.** 편의 인자가 아니라 비용 상한
장치다 — 선택으로 두면 모델이 파일을 통째로 부르고, r=4,000 이면 3회에 5.6배가 된다.

**`grep` 은 보관 소스 위에서 돈다.** `chunks.content` 에 걸면 비어있지 않은 줄의
8.5~12.7% 가 빠진 코퍼스를 뒤지게 되어 "없다"가 거짓이 된다. 줄 가르기는 DB 가 한다
(`unnest(string_to_array(content, E'\n')) WITH ORDINALITY`) — 파이썬으로 끌어오면
매칭 없는 파일까지 전부 전송된다.

### grep 에서 두 가지를 놓쳤다가 고쳤다

- **CRLF.** `\n` 으로 가르면 모든 줄이 `\r` 로 끝나 인용이 한 글자씩 어긋난다.
  `rtrim(text, E'\r')` 로 뗀다.
- **LIKE 와일드카드.** `_` 가 와일드카드라 `find_user` 가 `findXuser` 에도 걸린다.
  모델이 "있다"고 본 것이 실제로는 없는 이름이 되므로 이스케이프한다.
  정규식(`~*`)을 안 쓴 이유도 같은 계열이다 — 모델이 지어낸 패턴이 백트래킹으로 DB 를 문다.

### 상한 셋 — 산식에서 나온 값이다

| 상수 | 값 |
|---|---|
| `claude_client.MAX_TOOL_ROUND_TRIPS` | 3 |
| `tools.MAX_TOOL_RESULT_TOKENS` | 800 |
| `tools.MAX_GREP_MATCHES` | 30 |

`P=1,140 · q≈40 · a_tool=150 · a_final=330 · r=800` 을 조사의 산식에 대입하면

    R=3 (호출 4회)  $0.020432  →  2.51배  ✓
    R=4 (호출 5회)  $0.029840  →  3.66배  ✗

> **여기 `r=800` 과 위 조사표의 `r=1,500` 은 모순이 아니라 다른 양이다.**
> 실행 전 점검에서 이 둘이 섞여 있는 것이 드러나 갈라 적는다.
>
> | | 무엇 | 무엇을 정했나 |
> |---|---|---|
> | `r=1,500` (위 '하이브리드가 순수 tool use 보다 비싸다') | **가정.** 캡이 생기기 전 조사가 잡은 전형적 결과 크기 | 3.78×/2.11× → **순수 tool use 로 간 근거** |
> | `r=800` (여기) | **상한.** `MAX_TOOL_RESULT_TOKENS`. 모든 결과가 캡에 닿는 최악 | 2.51× → **`MAX_TOOL_ROUND_TRIPS=3`** |
>
> **실측이 대조할 상대는 가정(1,500)이지 상한(800)이 아니다.** 평균이 800 아래인 것은
> 캡이 있으니 당연하고 아무것도 증명하지 않는다. 그래서 기록의 `result_tokens` 는
> **자르기 전** 크기이고(캡이 무엇을 막았는지), 실제로 간 크기는 `sent_chars` 로 따로
> 남긴다. 청구된 토큰의 정본은 이 둘이 아니라 호출별 `input_tokens` 다.

**3 이 3.0 아래에 남는 마지막 값이다.** 남는 0.49배는 effort 가 만드는 사고 토큰
(출력으로 청구된다)이 `a_tool` 추정을 넘길 여지를 덮는 몫이다.
**셋 중 하나만 고치면 이 산식이 깨진다** — STATUS.md §1.5 에 근거째로 적었다.

절단은 **문자 수로 먼저 거르고 토큰으로 판정한다.** `estimate_tokens` 는 2.0자/토큰이라
코드에서는 실제보다 많게 잡으므로, 추정이 상한 안이면 실제도 안이다 — 그때는 토큰 계산
왕복을 아낀다(`_try_full_injection` 이 바이트로 먼저 거르는 것과 같은 구조).
자른 경우 **잘렸다는 문구를 결과 안에 넣는다** — 안 넣으면 모델이 잘린 것을 "없다"로 읽는다.

### 한도에 닿았을 때 `tool_choice` 를 쓰지 않았다

`tool_choice` 변경은 tools·system 캐시는 살리지만 **messages 캐시를 무효화**한다.
그러면 마지막 호출이 스냅샷 접두사를 통째로 정가로 다시 계산한다 — 접두사가 큰 저장소일수록
손해가 크다. 대신 *"도구 호출 한도에 도달했습니다…"* 를 **마지막 사용자 메시지 꼬리에**
덧붙인다. 꼬리는 브레이크포인트 뒤라 접두사를 건드리지 않는다.

### 한 질문이 호출 여럿이 됐다

`_call()` 은 1회 호출 전용이라 그대로 두고(요약이 쓴다) `_call_loop()` 을 더했다.
`_raw_call()` 로 파라미터 조립을 한 곳에 모았다.

- 반환 dict 는 `_call()` 과 **같은 키 집합 + `round_trips`·`hit_round_trip_cap`** 이다.
  `run_log.append_run()` 과 `billable_tokens()` 가 그대로 재사용된다
- 토큰 넷과 `llm_ms` 는 **전 호출의 합**이다. 마지막 호출만 세면
  `rate_limit.record_tokens(billable_tokens(result))` 가 사실상 꺼진다 — 테스트로 못 박았다
- 응답 블록을 **그대로** 되돌린다. 텍스트만 뽑으면 `tool_use` id 가 사라져 다음 요청이 거부된다
- 결과는 **한 user 메시지에 모아** 보낸다. 나눠 보내면 모델이 병렬 호출을 그만둔다
- 실패한 도구도 `is_error: true` 로 돌려준다. 빠뜨리면 짝 없는 `tool_use` 로 API 가 거부한다

`round_trips` 를 `runs` 테이블에 남겼다(`FIELDS` 15→16). **실사용의 라운드트립 분포는
여기서만 나온다** — 하네스는 평가셋 질의만 본다. `FULL_INJECTION_MAX_TOKENS` 를 4세션
표본으로 역산해 두고 아직 다시 못 뽑은 것과 같은 실수를 되풀이하지 않으려는 열이다.

### 도구를 안 붙이는 경우는 둘뿐이다

전체 주입 스냅샷(소스가 이미 접두사에 다 들어가 있다)과 색인이 아직 안 끝난 스냅샷.
**둘 다 스냅샷 속성이고 한 대화 안에서 바뀌지 않는다** — 저장소 이름이나 요청 내용으로
가르지 않는다. 계획 문안은 "도구 목록은 항상 같다"였는데, 전체 주입 팔은 기준선에서
`tools` 없이 측정한 모양이라 프로덕션이 달라지면 그 측정이 무효가 된다. 그래서 갈랐다.

**보관된 소스가 없는 스냅샷은 도구를 그대로 받는다.** 배포 직후에는 모든 옛 스냅샷이
여기 해당한다(소스 보관이 그 뒤에 생겼고 재색인은 수동이다). `read_file`·`grep` 이
"보관된 소스가 없습니다 — search_code 를 쓰세요"로 답하고 모델이 선회한다.

### 프롬프트는 두 군데만 고쳤다

- 코드가 오는 경로에 도구 셋을 추가했다. `read_file` 은 `number_lines()` 를 재사용하므로
  전체 주입 번들과 **같은** `{n}|{line}` 형식이다 — **셋째 형식이 아니다**
- "조각 안에서 특정 줄을 세어 짚지 마세요"의 적용 대상을 **`search_code` 결과로 좁혔다.**
  안 좁히면 모델이 가장 믿을 만한 근거(원본에서 직접 잘라 온 `read_file` 결과)를 못 믿는다
- **§A 계약**을 넣었다 — 도구가 보는 범위는 색인이 수집한 파일 집합이고,
  "저장소에 없다"와 "수집 범위에 없다"는 다른 말이다

`REFUSAL_PHRASES` 두 개는 리터럴로 남겨 정합성 검사가 계속 깨질 수 있게 뒀다.

### 거절 채점기 구멍을 같은 커밋에서 메웠다

`REFUSAL_SCOPES` 에 `(?:읽어|열어|확인해|찾아|살펴)\s*본` 을 더했다(5→6).
도구 경로는 "검색된 범위" 대신 **자기가 한 행동**으로 스코프를 말한다.

**기존 89건으로 재채점했다 — 무과금, API 호출 0회.** 거절 24/24 유지, 인용 정확도
네 팔 모두 한 자리도 안 변함, 정답 인용과의 충돌 0건.

다만 **89건에는 도구 경로 답변이 없어서 재채점으로는 새 계열이 동작하는지 증명되지
않는다.** 그래서 `test_citation_scoring.py` 에 세 건을 고정했다 — 잡아야 할 문장,
**부정 술어 없이 행동만 말한 문장은 거절이 아니라는 것**(이쪽이 위험하다. 도구를 쓰면
"읽어 본 파일에서 확인했습니다" 처럼 행동을 먼저 말하고 답하는 형태가 흔하다),
그리고 양보 규칙이 도구 경로에도 걸린다는 것.

### 하네스에 `tool` 팔을 더했다

`_arms_for()` 가 이제 `(rag, full, tool)` 또는 `(rag, tool)` 을 준다. **`rag` 를 같은
실행에서 다시 재야 한다** — 프롬프트를 고쳤으므로 옛 인용 기준선이 무효다.

보고서에 `질문당 도구호출`·`한도에 닿음`·`RAG 대비 배수`를 넣었다. 배수를 눈으로 나누게

`없-`+어미(연결형 포함) · `[탐색 동사]+지 않` · 가능성 부정. 스코프는 범위 명사 하나를
**양쪽 어순으로** 감싼다(`전체 X` / `X 전체`). 재채점(89+67=156건, 무과금 $0)에서
12/15 가 잡히고 **정답 인용과의 충돌은 0건**이다.

**이것은 이번 실수가 아니라 이 자의 구조적 한계다.** 문구 매칭인 이상 다음에도 샌다 —
자를 고칠 때마다 기준선을 다시 읽어야 하고, 그게 무과금인 것이 이 설계의 값이다.

### 남은 3건은 자가 맞다 — 요구를 바꿨다

`md_ab_06/rag`(첫 문장이 답변, 거절은 마지막 문단) · `ap_ab_03/tool`(첫 문장이 "…에
대한 것이지 …아닙니다" — 동일성 부정이지 부재가 아니다) · `ap_ab_06/tool`(양보).

셋을 잡으려면 첫 문장 제한이나 양보 규칙을 풀어야 하고, 그 순간 "지어낸 답 + 면피
한 줄"이 거절로 통과한다. **자를 틀리게 만들어야 만족되는 요구는 요구가 틀린 것이다** —
0단계에서 같은 이유로 3번 요구를 바꿨다. `NOT_A_REFUSAL_OPENING` 목록으로 면제하되
**새로 새는 건이 생기면 여전히 깨지게** 두고, 면제가 낡으면(이제는 잡히면) 그것도
깨지는 테스트를 함께 뒀다.

### 내가 넣은 계열은 한 건도 안 걸렸다

`(?:읽어|열어|확인해|찾아|살펴)\s*본` 을 "도구 경로는 자기 행동으로 스코프를 말할
것"이라 보고 미리 넣었는데, **67건에서 한 건도 안 걸렸다.** 모델은 도구를 써도
스코프를 여전히 `검색된 범위`·`검색 결과`로 말한다. 예상이 빗나갔다.
지우지 않고 두는 것은 답변 양식이 바뀔 여지 때문이지 근거가 있어서가 아니다.

### 기준선 팔도 움직였다 — 노이즈와 구분되지 않는다

프롬프트를 고쳤으므로 `rag` 를 같은 실행에서 다시 쟀다. 인용 정확도가
`air 0.7059 → 0.7647` · `marryday 0.6875 → 0.6875` · `apns4j 0.75 → 0.8125` 이다.

정확히 한 건 차이이고, **노이즈와 구분되지 않는다.** 프롬프트 효과로 읽지 말 것.

## 1단계 판정 — 큰 저장소는 tool use, 작은 저장소는 전체 주입 - 2026-08-22

**코드 변경 없음.** 현행 구현이 이 판정과 이미 일치한다 — 판정을 기록만 한다.

    전체 주입 임계값을 넘는 스냅샷 → tool use 를 켠다
    임계값 이하 스냅샷           → 전체 주입 유지 (도구를 붙이지 않는다)

기준은 0단계가 측정 **전에** 고정한 A(인용) → B(거절) → C(비용) 순서다.

### 근거는 air 다

| | 기준선(rag) | tool | 차이 |
|---|---|---|---|
| 인용 정확도 | 0.7647 | **1.0** | **+0.235** |
| 거절 정확도(재채점) | 1.0 | 1.0 | 0 |
| 질문당 비용 | $0.009141 | $0.016109 | **1.76배** (상한 3.0) |

**+0.235 는 한 건(0.0588)의 4배다.** 프롬프트 변경이 기준선을 움직인 폭(+0.06 = 한 건)과
크기가 명확히 갈린다 — 이 차이는 노이즈로 설명되지 않는다.
기준 A 통과, B 동률, C 는 상한의 절반 아래다.

### marryday 는 독립 근거가 아니다

인용 0.6875 → 0.75, **+0.0625 는 정확히 한 건이다.** 노이즈와 구분되지 않으므로
**이 세트만으로는 아무것도 말하지 않는다.**

**그렇다고 판정을 바꾸지도 않는다.** air 와 **같은 코드 경로**이고(둘 다 임계값 초과 →
RAG 색인 → 도구), 세트별로 켜고 끄는 분기는 저장소 이름으로 가르는 것과 같아서
안 만든다(CLAUDE.md §7). marryday 는 **판정을 뒤집지 않은 것**이지 판정을 받친 것이 아니다.
거절은 0.8333 → 1.0, 비용 1.99배로 A·B·C 어디에도 걸리지 않는다.

### apns4j 는 기각 — 전체 주입이 이긴다

인용 `full 1.0 > tool 0.9375`. 기준 A 는 "떨어지면 기각"이므로 이 저장소 성격
(임계값 이하)에서는 tool use 를 켜지 않는다.

**이건 이미 구현된 결정이 측정으로 확인된 것이다.** 전체 주입 스냅샷에 도구를 붙이지
않기로 한 것은 "소스가 이미 접두사에 다 들어가 있어 부를 이유가 없다"는 이유였고,
측정이 그 판단을 지지한다. **코드는 그대로 둔다.**

### apns4j/tool 의 거절 0.6667 은 회귀가 아니다

답변 원문을 읽었다. **날조 0건이다.** 못 잡힌 2건 중 하나(`ap_ab_06`)는 양보
("옵션은 있지만 … 발견되지 않았습니다")라 **양보 규칙이 의도대로 동작한 것**이고,
다른 하나(`ap_ab_03`)는 첫 문장이 동일성 부정("…에 대한 것이지 …아닙니다")이라
부재 선언이 아니다.

**문구 매칭은 "지어내지 않았는가"의 대리 지표다**(07 docstring). 두 팔에 같은 자를 대므로
비교에는 쓰지만 **절대값을 품질로 읽으면 정반대로 틀린다** — 0단계에서 apns4j/rag 의
0.0 이 정확히 그런 바닥 효과였다.

### 캡은 그대로 둔다

라운드트립 상한에 걸린 질의의 인용 정확도가 **19/21 로 안 걸린 쪽(1회 12/12·2회 13/16)과

## 2단계 백엔드 — 인용 파서를 하나로 합치고 파일 조회를 열었다 - 2026-08-22

브랜치 `feat/citation-ui`. **행 번호 정확도 72.4% 를 화면에서 보이게** 만드는 작업의

### 먼저 확인한 것 — ReactMarkdown offset 은 된다

이게 안 되면 설계가 통째로 달라지므로 먼저 봤다.

  `if (from.position) to.position = position(from)` — **텍스트 노드에도 원본 offset 이

→ rehype 플러그인이 hast 텍스트 노드를 원본 offset 으로 찾아 쪼갤 수 있다.
**프론트에서 정규식을 새로 짤 필요가 없다.**

**함정 하나**: `text.js` 가 `trimLines()` 로 줄 앞뒤 공백을 지워서
`노드 안 인덱스 = offset − node.position.start.offset` 이 어긋날 수 있다. 그래서 백엔드가
offset 과 함께 **일치한 글자(`marker`)** 를 같이 보낸다 — 프론트는 offset 으로 **노드를
고르고** `indexOf(marker)` 로 **노드 안 위치를 정한다.**

**두 번째가 통과했다.** 짧은 조각 테스트가 `a=b`(3자)를 써서 상한이 6이든 4든 같은
결과(버림)를 냈다. **경계에 딱 맞춰야 갈린다** — `a = b`(5자)로 바꾸고 `a == b`(6자)로
반대쪽도 고정한 뒤에야 변이가 깨졌다. 어제 같은 함정을 겪고 CLAUDE.md §4 에 규칙까지
적어 뒀는데 또 걸렸다.

**하네스는 이 변이를 못 잡는다** — 실제 답변에 4~5자짜리 코드 모양 조각이 없어 판정이
하나도 안 움직였다. `-m evaluation` 수치는 **규칙이 바뀌었는지의 감시선이지 모든 규칙의
보증이 아니다.** 경계값은 단위 테스트가 지킨다.
