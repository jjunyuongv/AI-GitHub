## 무엇을 뽑을 수 있는지 먼저 셌다 - 2026-08-24

브랜치 `chore/production-baseline`. STATUS.md §4 에 "프로덕션 기준선은 `runs` 의 실사용
기록으로 뽑을 것"이 남아 있었다. **값을 정하기 전에 표본부터 셌다** — 작은 표본으로 상수를
정하는 것이 바로 그 항목이 경계한 실수라서.

**표본은 51행이 전부다.** 먼저 확인한 것은 `logs/runs.jsonl` 31행과 DB 를 합산해도 되는가였다.
ts 를 대조하니 **31/31 이 전부 DB 에 있었다** — `migrate_runs_to_db.py` 로 이관된 것이라
합산하면 이중계상이다.

축마다 표본이 달랐다.

| 축 | 표본 | 판정 |
|---|---|---|
| 일일 실사용 | `rate_limit_daily` 9일 | 기준선 |
| 질문당 실비 | analyze 7 · chat 29 | 기준선 |
| 접두사 | 저장소 4개 | 관측치 |
| `round_trips` | 12건 (39건은 열 추가 전 NULL) | 관측치 |
| 세션당 질문 수 | 6세션 | 관측치 |
| `stop_reason` | 1건 | 집계 불가 |

**그리고 표본 크기보다 중요한 것이 하나 있었다 — 51행이 전부 개발자 본인의 검수 트래픽이고
외부 사용자 트래픽이 0이다.** 500행이 쌓여도 개발자 트래픽이면 기준선이 아니다. 그래서
"실사용 기록이 쌓이면 다시 뽑을 것"의 조건을 **행 수가 아니라 트래픽 성격**으로 다시 썼다.

## 접두사를 2배로 적어 두었던 것을 잡았다 - 2026-08-24

접두사 분포를 뽑다가 같은 저장소가 16,240 과 24,360 을 오가는 것이 눈에 걸렸다.
`cache_write` 와 `cache_read` 를 나눠 보니 답이 나왔다.

**`runs` 한 행은 질문 하나인데 그 안에 API 호출이 `round_trips + 1` 번 있고, `_call_loop`
이 토큰을 합산해 한 줄로 남긴다**(STATUS §2.4 에 적혀 있는 그대로다). 그래서 `cache_read`
는 접두사가 아니라 **접두사 × 읽은 호출 수**다. 쓰기는 캐시를 만들 때 한 번뿐이라 합산돼도
접두사 그대로다.

근거는 `07-answer-quality.md:998` 의 표 자신이었다 — 같은 행에 쓰기 8,120 과 읽기 16,240 이
나란히 있는데, 읽기 쪽을 접두사로 읽었다. 세 행이 전부 8,120 의 배수로 맞는다
(왕복 2 → 쓰기 1 + 읽기 2 · 왕복 2 → 읽기 3 · 왕복 1 → 읽기 2).

검산을 스크립트에 넣었다. `round_trips` 가 있는 10건 전부 정수배로 맞았고 어긋난 행은 0이다.

**고친 것:** STATUS.md §4 의 "접두사가 14배 다르다 · 프로덕션 16,240" → **7배 · 8,120**.
비용 수치($0.0161 vs $0.0225)는 영향을 받지 않는다 — 그것은 실측 `cost_usd` 라서.

**왜 안 잡혔나.** 접두사와 읽기 토큰이 같은 값인 상황(도구 없음 = 호출 1번)에서만 재 왔다.
도구가 붙어 호출이 여러 번이 되면서 갈렸는데, 그때 나온 새 숫자를 옛 해석으로 읽었다.
**변이 테스트의 대역 데이터가 "두 동작이 다른 결과를 내도록" 설계돼야 한다는 것과 같은
성질이다**(CLAUDE.md §4) — 왕복 1회짜리 표본만 봤으면 영영 안 갈렸다.

## 임계값 재역산 — 표본 컷이 답을 뒤집었다 - 2026-08-24

`FULL_INJECTION_MAX_TOKENS`(57,000)의 근거 표본이 4세션 → 6세션으로 늘었다.
산식은 `04-tasks-1-2.md:120-133` 의 것을 그대로 쓰고, `C_rag`·`p_in`·`snip` 을 **고정**한 채
`w̄` 만 움직였다 — 로그가 "이 값이 임계값을 지배한다"고 적어 둔 축을 격리하기 위해서.

| 세션 표본 | w̄ | S_max |
|---|---|---|
| 원래 4세션 `[3,6,2,2]` | 0.4538 | 56,909 |
| 6세션 전부 `[1,2,3,5,8,10]` | 0.3379 | 76,430 |
| 하루 안에 끝난 세션만 `[1,2,5]` | 0.5312 | 48,617 |

**답이 뒤집힌다.** 전부 넣으면 57,000 이 34% 여유가 있고, 이어 쓴 세션을 빼면 오히려
17% 헐겁다. "빠듯한가"에 단일한 답이 없다.

**8·10·3 짜리 세션은 개발자가 여러 날에 걸쳐 이어 쓴 것이다**(8/16→8/22, 8/17→8/21,
8/18→8/23). `w̄` 는 긴 세션에서 캐시 쓰기 1.25배가 나눠지는 것을 반영하는데, **캐시 TTL 이
5분이라 이어 쓴 세션에서는 그 나눔이 실제로 일어났는지조차 알 수 없다.** 표본이 6개뿐이라는
것보다 이쪽이 중요하다.

**값은 바꾸지 않았다.** 2세션 늘어난 표본으로 상수를 움직이는 것이 §4 가 경계한 그 패턴이다.

산식 자체가 틀어지지 않았는지는 대조군으로 본다 — 원래 표본 `[3,6,2,2]` 를 넣으면 56,909 가
나와야 하고, 스크립트가 매번 확인한다. (로그의 56,991 과 82, 0.14% 차는 로그 쪽 반올림이다.
로그가 적어 둔 "질문이 전부 6회면 약 88,000" 도 88,553 으로 재현됐다.)

## 등재 위치를 §5 로 정했다 - 2026-08-24

**§1 이 아니다** — 코드 상수를 AST/import 로 대조하는 자리인데 실측값은 대조할 심볼이 없다.
**§2 도 아니다** — §2 항목은 전부 코드 경로가 붙고 `test_narrative_paths_exist` 가 그것을
검사하며, §2 는 "최종 확인" 해시 하나로 낡음을 잰다. 실측값은 **재집계 시점이라는 자기
시계**를 가져서 섞으면 두 시계가 엉킨다.

그래서 §5「실측 기준선」을 새로 만들고 5.1(기준선) / 5.2(관측치)로 갈랐다.
`Back/app/` 은 한 줄도 안 바꿨으므로 §2 의 "최종 확인" 해시는 그대로 둔다.

**표 형식 함정 하나** — `test_no_malformed_rows` 는 `|` 가 정확히 5개인 줄(4열 표)을 전부
상수 표 행으로 간주해 정규식에 안 걸리면 실패시킨다. §5·§4 의 새 표는 전부 3열로 만들었다.

재집계 스크립트는 `Back/scripts/aggregate_runs.py` 다. SELECT 만 하고 `init_schema()` 도
부르지 않는다. 출력 순서는 §5 의 항목 순서와 같아서, 표본이 쌓이면 돌려서 그 절만 갱신하면 된다.

**`DAILY_LLM_CALL_LIMIT` 이름 문제는 정하지 않았다.** 선택지 셋과 각각의 파급을 §4 에
적어 두었다. 상수 이름을 바꾸면 `.env`·`config.py`·테스트가 같이 움직이고, 무엇보다
**배포 `.env` 의 옛 이름이 조용히 무시된다.**
