## 로그인하면 목록 밖 저장소도 받는다 (2026-08-30)

**로컬 전용이다. 배포하지 않는다.** LLM 을 한 번도 부르지 않았다.

### 왜 목록의 역할이 바뀌었나 — 이것이 이 작업의 전부다

`allowlist.py` 머리말에 이렇게 적혀 있었다:

> **로그인이 생겨도 이 목록은 따로 필요하다.** 로그인은 누가 썼는지를 알려줄 뿐
> 무엇을 분석할지는 안 가른다.

**그 문단이 쓰였을 때는 청크 상한이 없었다.** 목록이 크기를 막는 유일한 방어선이라,
열면 큰 저장소 하나가 색인을 통째로 세울 수 있었다. 지금은 `MAX_INDEX_CHUNKS`(300)가
한 건당 크기를 막는다. 그래서 목록의 역할이 **크기 방어에서 "로그인하지 않은 사람의
범위 제한"으로 좁아졌다.**

**첫 문단은 안 고쳤다.** "색인은 큐가 하나뿐이라 큰 저장소 하나가 그 뒤의 모든 색인을
세운다"는 여전히 참이다 — 청크 상한은 저장소 **하나**의 크기를 막을 뿐 줄 서는 것
자체를 안 막는다. 그것이 큐 귀속을 STATUS §4 로 보낸 근거다.

### 상태가 셋이다 — `user_id is None` 하나로는 못 가른다

`login_session.current_user_id()` 는 로그인이 꺼져 있어도 None 을 주고 켜져 있는데
익명이어도 None 을 준다. **그 둘이 한 값에 뭉개지는데 서로 다른 문구를 내야 한다** —
꺼져 있으면 로그인하라고 할 수 없다(누를 버튼이 화면에 없다).

그래서 `check(owner, name, user_id=None)` 은 판정만 하고, 문구는 `_blocked_message()`
가 `oauth.enabled()` 를 보고 고른다. **`allowlist` 에 `oauth` 의존성이 하나 늘었다.**
호출부가 플래그를 넘기는 안도 있었지만, 그러면 "꺼지면 도입 전과 같다"는 계약이
`analyze.py` 로 새어 나가 순수 단위 테스트로 못 잡는다.

**`oauth.enabled() and user_id is not None` 으로 이중 확인하지 않았다.** 로그인이
꺼졌는데 `user_id` 가 들어오는 경로가 코드에 없고, 판정을 두 값에 걸면 어느 쪽이
이기는지를 또 기억해야 한다.

### `.env` 전후 — 넣기 전에는 아무 효과가 없었다

`Back/.env` 에는 `ALLOWED_REPOS` 키가 **아예 없었다.** 그래서 `allowlist.enabled()`
가 False 였고, **로그인 여부와 무관하게 전부 통과했다.** 기능을 넣어도 이 상태에서는
아무것도 안 갈린다.

`ALLOWED_REPOS=teaey/apns4j,jjunyuongv/air` 를 넣은 뒤(로컬은 로그인이 켜져 있다):

| | `teaey/apns4j` (목록) | `pallets/flask` (목록 밖) |
|---|---|---|
| 익명 | 통과 | **거절 403** |
| 로그인 | 통과 | **통과** |

익명 차단 문구도 로그인 안내가 붙은 쪽으로 떴다. **`.env` 는 커밋되지 않으므로 이
표를 재현하려면 그 값을 직접 넣어야 한다.**

### 변이 셋을 실제로 넣어 봤다

| 변이 | 깨진 테스트 |
|---|---|
| ① 문구 분기 제거(언제나 옛 문구) | `test_로그인이_켜져_있고_익명이면_로그인_안내를_받는다` **1건** |
| ①-역 (언제나 로그인 안내) | `test_로그인이_꺼져_있으면_문구가_도입_전_그대로다` **1건** |
| ② 로그인이면 남용 상한을 건너뜀 | 예약 횟수 1건 + 429 응답 1건 = **2건** |
| ③ 로그인이 켜져 있으면 청크 상한을 끔 | 새 파라미터 조합 `[11-True-test-client-id]` **1건** |

①과 ①-역을 둘 다 넣은 이유는 한쪽만으로는 **문구를 뭉개는 방향**만 잡히기 때문이다.
②는 호출 횟수와 사용자에게 보이는 응답을 따로 잰다 — 앞은 새는 것을, 뒤는 그 결과를 본다.

### 변이 ③ 에서 예상보다 많이 깨졌다 — 환경이 샌 것이었다

③ 을 넣었더니 **4건**이 깨졌다. 새 조합 하나는 의도한 것이고, 나머지 셋은 로그인
상태를 안 고정한 기존 청크 상한 테스트였다. 이 기계의 `Back/.env` 에
`GITHUB_OAUTH_CLIENT_ID` 가 있어 `oauth.enabled()` 가 참이었기 때문이다.

**로그인이 꺼진 기계에서는 그 셋이 통과하고 새 조합 하나만 깨진다.** 즉 기계에
상관없이 이 변이를 잡는 것은 새로 넣은 파라미터 테스트뿐이다.

`conftest.py` 가 환경변수를 고립시키지 않는다는 것을 미리 알고 새 테스트에는 로그인
상태를 전부 고정해 두었는데, **그 판단이 맞았다는 것을 변이가 증명한 셈이다.**
기존 허용 목록 테스트 4건에도 `login_off` 를 한 줄씩 붙여 갈래를 명시했다
(이름과 본문은 그대로 뒀다). TROUBLESHOOTING 에 한 줄 남겼다.

### `.env` 를 고치자 무관한 테스트 15건이 깨졌다

목록을 넣고 전체를 돌리니 `test_analyze_api.py` 가 무더기로 깨졌다. 그 파일 대부분이
`facebook/react` 로 요청하는데 이제 목록 밖이라 403 이다. `allowlist.ALLOWED` 는
**임포트할 때 1회** 계산되므로 개발 `.env` 가 그대로 테스트로 새어 든 것이다.

**테스트가 "개발 기계에는 허용 목록이 없다"에 기대고 있었다.** 그 파일에는 이미
`isolated_files` autouse 픽스처가 같은 이유로 남용 상한을 끄고 있었는데, 허용 목록은
빠져 있었다. 같은 자리에 `ALLOWED = ()` 를 더해 껐다 — 목록을 재는 테스트는 각자 켠다.

**이 실패가 이번 작업에서 제일 값이 나갔다.** 기능 자체는 변이 셋으로 확인됐지만,
이건 설정 하나를 바꾸면 무관한 테스트가 깨진다는 구조적 문제였고 `.env` 를 실제로
고쳐 보지 않았으면 안 나왔다. TROUBLESHOOTING 에 한 줄 남겼다.

### `USER_DAILY_LIMIT`(100)은 안 건드렸다

**자가 틀렸다.** 이 상한이 세는 것은 질문 수이지 색인한 저장소 수가 아니다 —
100 을 10 으로 낮춰도 큰 저장소 10개면 큐는 똑같이 밀린다. CPU 를 실제로 막는 것은
`MAX_INDEX_CHUNKS`(로컬 300청크 ≈ 57초)이고 그것은 로그인과 무관하게 걸린다
(새 테스트가 그것을 고정한다).

역산 근거("서비스 상한 500 을 최소 5명이 나눠 쓴다 → 100")의 분자도 그대로다.
최악을 계산해도 한 사람이 상한을 다 써서 질문 100건이 전부 새 저장소여야 100 × 57초
≈ 95분의 직렬 CPU 이고, 실사용 8건이면 약 7.6분이다.

**문제는 총량이 아니라 한 사람이 큐를 독점할 수 있다는 구조**이고, 그건 상한 값이
아니라 큐 귀속으로 풀 일이라 STATUS §4 에 적었다.

### private 저장소

`oauth.py` 는 **scope 를 아예 요청하지 않는다**(`read:user` 도 아니다). 하지만 그것이
이유가 아니다 — 저장소는 언제나 서버의 `GITHUB_TOKEN` 으로 읽으므로, 로그인을 어떻게
바꿔도 비공개는 안 열린다. 그래서 안내 문구를 "아무 저장소나"가 아니라 **"공개 저장소는
무엇이든"** 으로 쓰고 괄호로 한 번 더 못 박았다. 없으면 로그인한 사람이 자기 비공개
저장소를 넣어 보고 404 를 받는다.
