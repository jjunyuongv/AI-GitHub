## 조사 — 색인 시간을 무엇이 정하는가 (2026-08-29)

**무과금.** 코드와 옛 기록을 읽었을 뿐이다.

로그인은 붙었는데 `ALLOWED_REPOS` 가 그대로라 아직 아무 저장소도 못 넣는다. 목록을
푸는 것을 막는 것이 색인 시간이라, 그것부터 쟀다.

### 색인을 탈지 말지를 정하는 값은 하나뿐이다

`FULL_INJECTION_MAX_TOKENS`(57,000) 이다. 그 아래는 전체 주입으로 0.5초에 끝나고,
넘으면 색인이 시작된다. 바이트로 환산하면 **소스 약 115~135KB** 가 경계다
(실측 바이트/토큰 비 2.05·2.41).

`FULL_INJECTION_MAX_SOURCE_BYTES`(500KB)는 아무것도 새로 자르지 않는다. 토큰으로
환산하면 21만~24만이라 57,000 의 4배다 — 여기 걸리는 저장소는 토큰을 세도 어차피
떨어진다. 이 값이 하는 일은 큰 본문을 토큰 세기 API 로 안 보내는 것뿐이다.

**경계 위에는 시간을 막는 값이 하나도 없다.** `MAX_STORED_SOURCE_BYTES`(20MB)는
원문 보관만 끄고 색인은 그대로 돌며, `MAX_HANDOFF_CHARS`(20MB)는 tarball 을 한 번 더
받게 할 뿐이다. `MAX_REPO_SIZE_KB` 는 git 히스토리를 재는 값이라 애초에 예측에 못 쓴다
(`config.py:16` 이 그렇게 적어 두었다).

### 시간을 정하는 것은 청크 수다. 파일 수가 아니다

| | air → marryday | |
|---|---|---|
| 파일 수 | 3.9배 | **파일당 청크가 5.0 vs 24.1 — 4.8배 어긋난다** |
| 소스 문자 | 20.2배 | 청크 18.5배와 9% 안에서 맞는다 |
| 청크 수 | 18.5배 | 시간 15.9배 |

청크당 시간은 169ms(air) vs 145ms(marryday)로 17% 어긋난다. **환경 탓이 아니다** —
같은 air 를 네이티브 40초와 Docker 42.7초로 쟀으니 컨테이너 몫은 7%다. 배치 안에서
짧은 청크가 긴 청크 길이에 맞춰 채워지는 것이 후보인데(`embeddings.py:28` 주석),
표본 둘로는 못 가린다.

### EC2 실측 (2026-08-29 갱신)

**air 236청크 = 7분 28초(448초) · apns4j 0.48초** — `index_builds` #2 의 시작·완료
시각이다. 처음에 적었던 배너 추정 11.6~12.7분은 **55~70% 과대**였다. 조사가 그 값을
"13.6% 지점의 추정이라 계측이 아니다"라고 표시해 둔 것이 맞았다.

- 청크당 **1.898초**
- 로컬 Docker(42.7초) 대비 **10.5배**, 네이티브(40초) 대비 11.2배.
  **전에 적은 16~18배는 틀렸다**
- 전체 주입은 EC2 0.48초 / 로컬 0.49초로 **환경 차이가 없다.** 임베딩이 없으니
  당연하고, 시간을 지배하는 것이 CPU 라는 것의 반대편 증거다

| 청크 수 | EC2 (1.898초/청크) | 소스 환산 |
|---:|---:|---:|
| 100 | 3.2분 | 약 50KB |
| 236 | **7.5분 (실측)** | 약 115KB |
| 400 | 12.7분 | 약 200KB |
| 600 | 19.0분 | 약 300KB |
| 1,000 | 31.6분 | 약 500KB |
| 2,000 | 1.05시간 | 약 1MB |
| 4,365 | **1.9~2.3시간** | 2.26MB |
| 42,000 | 22.1시간 | 20MB |

소스 1MB ≈ **1.1~1.2시간**이다. 4,365청크는 두 방식이 갈린다 — 청크당 시간으로
2.30시간, 로컬 총시간을 10.5배 한 것으로 1.85시간. **범위로 적는다.**

### 더 재야 하는 것

1. ~~EC2 실측 한 건~~ — **했다. 위 절이 그것이다**
2. 바이트→청크 비의 세 번째 표본 — 두 표본 다 한국어 주석이 많은 저장소다
3. t3.medium 의 CPU 크레딧 모드 — 아래 '남은 것'
4. 긴 색인의 뒷부분 곡선 — 실측 한 건은 236청크짜리라 짧다
5. 2 vCPU 에서 tarball 을 푸는 시간 — 잰 적이 없다

### 남은 것 — 자격증명이 없어 못 한 확인

t3.medium 은 버스터블이라 크레딧이 마르면 성능이 떨어지거나(standard) 추가 요금이
붙는다(unlimited). 확인하지 못했다 — `~/.aws/credentials` 가 `.bak` 으로 남아 있다.
콘솔에서 볼 것은 `CPUCreditBalance`·`CPUSurplusCreditsCharged` 와 인스턴스 Details 의
`Credit specification` 이다.

**실측이 나온 뒤 급한 정도가 내려갔다.** 2 vCPU 를 다 쓰면 분당 2크레딧을 쓰고
시간당 24를 버니 순소모가 시간당 96인데, 2.3시간짜리는 약 221크레딧이라 잔량 상한
576 안에 들어온다. **22시간짜리(20MB)는 여전히 바닥낸다** — 곧 이 확인은 큰 저장소를
받기로 정할 때 필요하지 지금 당장은 아니다.

## `EMBED_BATCH_SIZE` 를 규칙 해시에 넣는다 (2026-08-29)

위 조사에서 나왔다. `chunk_rule._constants()` 에 `EMBED_BATCH_SIZE` 가 **없어서**,
배치를 바꿔도 `rule_version()` 이 그대로였다.

### 왜 문제인가

배치는 청크 경계를 안 바꾼다. 대신 **같은 청크가 다른 벡터로 나온다**(코사인 평균
0.993 — int8 과 fp32 의 차이만큼 벌어진다, `05-tasks-a-b.md`). 해시가 안 움직이면
낡음 경고가 안 뜨고, 옛 배치로 만든 색인과 새 배치로 만든 색인이 겉으로 구분되지
않는다. **배치를 배포 기기에서 다시 재려던 참이라(STATUS §4) 이걸 먼저 고쳐야 했다** —
안 고치면 재측정이 어느 배치로 만든 색인을 보고 있는지 모른 채 돌아간다.

### 이름은 '청킹'인데 실제로는 색인 전체를 잰다

`rule_version()` 의 docstring 은 "청크의 모양"이라고 적혀 있었지만, **실제로 쓰여 온
뜻은 그것보다 넓다.** fp32 를 int8 로 바꿀 때 재색인 대상을 잡아 준 것이 이 해시였고
(`822bb217` 로 바뀌었다), 그때 달라진 것은 청크 경계가 아니라 벡터였다. 모델 이름이
이미 `_constants()` 에 들어 있는 것도 같은 이유다. 그래서 배치를 넣는 것은 뜻을
넓히는 것이 아니라 **적혀 있던 뜻을 실제에 맞추는 것**이다. docstring 을 함께 고쳤다.

### 지금은 벡터가 같은데 해시만 바뀐다 — 그래도 지금이 맞다

- 해시: `822bb217` → **`2b32a79f`** (로컬 `.env` 기준)
- 배치 값은 32 그대로다. 곧 **다시 색인해도 바이트 단위로 같은 벡터가 나온다.**
  이번 낡음 표시는 거짓이다.

**그런데도 지금 넣는다.** 나중에 넣으면 해시 변화와 벡터 변화가 같이 와서, 어느 색인이
옛 배치인지 구분할 수 없다 — 막으려던 바로 그 상태가 된다. 지금 치르는 값은 한 번의
거짓 낡음 표시이고, 그 값을 아는 채로 치르는 것이 낫다.

**다만 이 표시는 `chunk_rule.py` 가 경계한 바로 그것이다** — 주석만 고친 편집에
반응하지 않게 AST 를 정규화해 둔 이유가 "그 편집마다 전부 낡음으로 뜨면 아무도 이
표시를 안 믿게 된다"였다. 그래서 **거짓인 것을 여기 적어 둔다.** 배포에서 이 경고를
보면 재색인하지 않고 지나가도 검색 품질은 안 변한다. 반대로 **배치를 실제로 바꾼
뒤에 뜨는 경고는 진짜다.**

### 곁가지 — 배포와 로컬의 해시가 이미 다르다

로컬은 `822bb217` 을 내는데 `09-deploy.md` 는 배포 스냅샷이 `7d06885c` 라고 적어
두었다. 여기서 **접두어가 환경마다 다른 것 아니냐고 의심했는데 틀렸다.**
원인은 파이썬 판이었고, 다음 절에 있다. 접두어·모델·배치는 전부 같았다.

의심 자체는 근거가 있었다 — 해시에 들어가는 값 중 `.env` 에서 오는 것이 그 둘뿐이다.
**빠뜨린 것은 인터프리터도 입력이라는 점이었다.**

## `rule_version()` 이 파이썬 판에 반응했다 (2026-08-29)

바로 위 절의 곁가지에서 나왔다. 배포가 `7d06885c`, 로컬이 `822bb217` 인데
**코드도 `.env` 도 같았다.**

### 처음 세운 가설은 틀렸다

"5923bd5(OAuth)가 `config.py` 에 줄을 추가해서"라고 봤는데 **그 경로는 애초에 해시에
닿지 않는다.** `chunk_rule` 은 `from app.config import ...` 로 **값만** 가져오고,
모듈 소스를 읽는 곳은 `_normalized_source()` 뿐이며 그 대상은 `chunker.py` 의 함수
여섯 개다. 실제로 `git show 5923bd5 -- Back/app/config.py` 의 변경은 주석 문구와
OAuth 상수 넷뿐이고 `EMBEDDING_*` 는 한 줄도 안 건드렸다.

`chunker.py`·`chunk_rule.py` 블롭도 `6f29059`·`5923bd5`·`81faf2d` 에서 전부 같다.

### `.env` 값으로도 재현이 안 됐다

옛 `_constants()`(배치가 들어가기 전)를 재구성해 후보 20개를 훑었다 — 모델 4가지 ×
접두어 5가지(따옴표가 값에 남는 경우, 뒤 공백이 잘린 경우, 빈 값 등).

- 로컬 값으로 → `822bb217` (재현 성공)
- fp32 모델명으로 → `8e9937c1`. **`05-tasks-a-b.md` 에 적힌 int8 전환 이전 해시와
  정확히 같다** — 재구성이 맞다는 독립 근거다
- **`7d06885c` 는 20개 중 하나도 안 나왔다**

### 인터프리터였다

로컬 venv 가 **3.14.0**, 컨테이너가 **`python:3.12-slim-bookworm`** 이다.
`ast.dump()` 는 3.13 에서 기본 출력이 바뀌었다 — `show_empty` 인자가 생기고 기본이
`False` 가 됐으며, **`show_empty=True` 가 3.12 까지의 동작**이다.

| `ast.dump` 렌더링 | 해시 |
|---|---|
| `show_empty=False` (3.13+ 기본 · 로컬) | `822bb217` |
| `show_empty=True` (3.12 · 컨테이너) | **`7d06885c`** ← 배포 값과 일치 |

같은 함수의 결과가 4,764자 → 5,282자로 518자 차이 난다. **확정이다.**

### 버그로 본 이유

"주석 한 줄로 해시가 바뀌는가"의 답은 **아니다**였다. 그 원칙은 두 경로에 다 걸려
있다 — 청킹 함수는 AST 정규화, config 는 값만 읽기. **원칙은 멀쩡했다.**

깨진 것은 다른 축이고 더 나쁘다. **주석에 반응하지 않게 만든 그 장치가 판에 반응했다.**

- 파이썬 판은 청크 경계도 벡터도 안 바꾼다. 출력이 전혀 안 변하는 것에 반응하니
  거짓 신호다
- **스스로 낫지 않는다.** 배포(3.12)에서 재색인하면 `7d06885c` 가 저장되고
  로컬(3.14)이 그것을 낡음으로 읽는다. 반대도 같다 — 양쪽이 서로를 영원히 낡음으로 본다
- 그리고 **아무것도 안 깨졌다.** 배포에서 색인이 조용히 낡을 뿐이라 눈치챌 신호가 없었다

### 고친 것

- `_normalized_source()` 를 `ast.dump` → **`ast.unparse`** 로. 주석·docstring 무시는
  그대로고(주석은 AST 에 없고 docstring 은 위에서 지운다), 로직 변경은 그대로 잡힌다.
  재료가 4,764자 → 984자로 준다
- **3.12 에 `show_empty=True` 를 명시적으로 넘기는 안은 못 쓴다** — 그 인자가 3.13 에
  생겨서 컨테이너에서 `TypeError` 가 난다
- `ast.unparse` 도 stdlib 렌더링이라 판이 바뀌면 또 흔들릴 수 있다. 그래서
  `test_normalized_output_is_pinned` 이 표본 하나의 정규화 결과를 리터럴로 고정한다.
  **렌더링이 바뀌면 배포에서 색인이 조용히 낡는 대신 그 테스트가 깨진다** —
  이번에 없었던 것이 바로 그 신호다

해시: `822bb217`(배치 넣기 전) → `2b32a79f`(배치) → **`3d1494f9`**(unparse).
가운데 값은 브랜치 안에만 있고 밖에 존재한 적이 없다 — **머지를 한 번에 하므로
운영이 보는 변화는 `7d06885c` → `3d1494f9` 한 번이다.**

### 배포 색인은 재색인이 필요 없다 — 확정된 사실

**해시는 다르지만 벡터는 같다.** 근거 셋:

1. `chunker.py` 블롭이 배포 시점과 동일하다 → 청크 경계가 같다
2. 모델·접두어·배치가 같다(배포 컨테이너의 env 로 확인) → 같은 청크가 같은 벡터가 된다
3. 해시 차이가 `ast.dump` 의 **출력 서식**에서만 왔다는 것을 위에서 재현했다

**air 를 7분 28초 다시 돌릴 이유가 없다.**

다만 이 수정을 배포하면 저장값(`7d06885c`)과 계산값(`3d1494f9`)이 달라 **낡음 경고가
켜진 채로 남는다.** 거짓이므로 무시해도 검색 품질은 안 변하고, 다음에 자연스럽게
재색인할 때 꺼진다. 지금 끄고 싶으면 air 7분 28초 + apns4j 0.5초면 되지만
**필요해서 하는 일은 아니다.**

### 검증

- **진짜 검증은 배포에서만 된다. 아직 안 했다.** 고쳤다는 것은 두 판이 같은 값을
  낸다는 뜻인데, 로컬에 3.12 가 없어(`py -0` 에 3.14 뿐) 여기서는 잴 수가 없다.

  **그때까지는 "고쳤을 것"이지 "고쳤다"가 아니다.**
- **다음에 켤 때 하도록 절차에 등재했다** — `09-deploy.md` 재기동 절차 **7단계**.
  기억에 맡기지 않는다. 거기 `--build --force-recreate` 를 둘 다 붙이라는 것과,
  낡음 경고가 뜨는 것이 정상이며 재색인하지 않는다는 것도 함께 적었다

## 청크 상한 300 — 구현 (2026-08-29)

조사와 판정 방법은 승인된 플랜에 있다. 여기는 실제로 넣은 것과 그 과정에서 나온 것.

### 판정은 청킹 뒤에 한다 — 큐를 안 건드렸다

`run_build()` 가 이미 `chunk_files → set_total → embed_documents` 순서라 **청킹이 이미
임베딩 앞에 있었다.** 상한 검사를 그 사이에 한 줄 넣는 것으로 끝났고 큐도 워커도
그대로다. 조사 때 걱정한 "청킹을 큐 앞으로 빼야 하나"는 **다른 작업이었다** —
그쪽은 *대기 중인* 항목의 청크 수가 필요하고(자리 번호·예상 시간), 상한은 *지금
처리 중인* 항목의 수만 있으면 된다.

값도 쟀다. 프로덕션 경로(토큰 재분할 포함) 청킹이 **air 236청크 0.76초 ·
marryday 4,364청크 3.19초**다. EC2 배수 10.5배를 곱해도 air 약 8초 —
**상한이 지키는 9.5분의 1.8%** 다. 넘긴 저장소에서는 33초를 써서 2.3시간을 피한다.

바이트 추정을 안 쓴 이유는 흩어짐이다. 캐시 3개를 언어별로 갈라 보니 문자/청크가
java 431 · python 432 · javascript 546 · html 625 · **css 708** 로 **1.64배** 벌어진다.
저장소별 흩어짐(1.22배)이 작아 보이는 것은 언어가 섞여 평균이 나기 때문이다.

### `skipped` 를 새로 뒀다 — 이유는 문구가 아니라 재시도다

`failed` 를 재사용하면 스키마도 화면도 안 건드려도 된다. 그런데 **동작이 갈린다.**

`index_status.begin()` 은 **pending/running 일 때만** 중복을 막는다. 곧 종료 상태로
남은 스냅샷은 `chat.py` 가 질문마다 부르는 `start()` 가 **매번 새 빌드를 만든다.**
상한 초과에서 그러면 질문마다 tarball 재다운로드(15~20초) + 청킹이 영원히 돈다.
실패는 다시 해볼 값이 있지만 상한 초과는 같은 스냅샷에서 결과가 안 바뀐다.

그래서 `SKIPPED` 상태 + `is_skipped()` 를 두고 `start()` 가 그것을 보고 빠진다.
`test_a_failed_snapshot_is_still_retried` 가 반대쪽을 고정한다 — **`is_skipped()` 를
`status != 'completed'` 로 넓게 잡으면 재시도 경로가 통째로 막히는데, 그 테스트가
없으면 모르고 지나간다.**

**`CHECK` 제약은 한 곳만 고쳤다.** 플랜에는 2곳으로 적었는데, `snapshot_index_status`
쪽 `status` 는 `complete()` 가 `'completed'` 로만 쓰고 코드가 더 이상 읽지 않는다
(schema.sql 이 그렇게 적어 두었다). 상한 초과 빌드는 활성 포인터를 안 만들어 그 표에
닿지 않는다. `index_builds` 만 `DROP CONSTRAINT IF EXISTS` + `ADD CONSTRAINT` 로 다시 건다.

**`completed` + 청크 0개(전체 주입 흉내)는 안 썼다.** `is_ready()` 가 True 가 되어
도구가 붙는데 `search_code` 가 빈손이고, 모델이 그것을 "저장소에 없다"로 읽는다
(STATUS §2.4 가 경계한 상태).

### 감시선은 테스트가 아니라 로그다

데모 저장소가 상한을 넘으면 tool use 경로가 화면에서 사라지는데, 그 일은 push 로 새
스냅샷이 생길 때 일어나 **아무 신호가 없다.** 처음에는 평가셋 캐시를 읽는 테스트를
생각했는데 **셋 다 막혔다** — ① `Back/cache/` 가 커밋되지 않고 캐시는 2026-08-18
사본이라 살아 있는 저장소가 자라는 것을 못 본다 ② CI 가 없다 ③ 캐시 없으면 skip 이라
한 기계에서만 도는 테스트가 된다.

그래서 `run_build()` 의 같은 자리에서 `logger.warning` 한 줄로 한다. 실제로 색인되는
그 스냅샷을 재고, 빌드당 한 줄이라 상시 점등되지 않는다(`test_narrative_is_not_too_stale`
이 811/300 으로 영구 점등된 것과 다르다). "경고냐 실패냐"도 사라진다 — pytest 경고가
아니라 런타임 로그다.

**0.8 은 "경고 뒤 활주로"로 정했다.** 상한의 20%(300이면 60청크 ≈ 28KB)가 남는다.
air 는 236/300 = **78.7%** 라 **지금은 안 뜨고** 4청크 뒤에 뜬다 — 그만큼 붙어 있는
것이 400 대신 300+감시선을 고른 근거를 그대로 되비친다.

### 겪은 것

`caplog` 로 경고를 확인하는 헬퍼를 `r.message % r.args` 로 썼더니 `ValueError` 가 났다.
`r.message` 는 **이미 펴진 문자열**이라 다시 `%` 를 걸면 본문의 `%`(여기서는 `80%`)를
형식 문자로 읽는다. `r.getMessage()` 가 답이다. **테스트를 돌렸기 때문에 잡혔다** —
TROUBLESHOOTING 의 "만든 것은 한 번은 돌릴 것" 이 그대로 맞았다.
